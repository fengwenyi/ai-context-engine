# AI CONTEXT — AI 协作开发统一入口

> 本文件是 AI 协作开发的**唯一入口**。开始任何任务前，AI 必须先完整读完本文件。
> 本文件**完全通用**，可直接复制到任意新项目使用，无需修改。

---

## 一、AI 必读流程

每次接到任务，AI 严格按下列顺序执行，缺一不可：

1. **读项目介绍** → 打开 [`project/项目介绍.md`](./project/项目介绍.md)，了解当前项目有哪些端、代码结构、技术栈、约定的代码路径。
2. **判断场景** → 根据下面的"场景路由"，确定属于场景 1 / 2 / 3，进入对应 workflow。
3. **改动方案先行** → 实现任何代码前，必须先输出"改动方案"等待用户确认（详见第三节）。
4. **按 workflow 执行** → 走对应场景的标准步骤，使用对应模板。
5. **沉淀** → 完成后更新功能文档、CHANGELOG、必要时写 `project/ai_files/` 笔记。

---

## 二、场景路由

| 场景 | 触发条件 | 对应 workflow |
|---|---|---|
| **场景 1：项目设计** | 还没项目，从 0 设计产品/技术/架构 | [`method/workflows/01-项目设计.md`](./method/workflows/01-项目设计.md) |
| **场景 2：新系统/新模块开发** | 项目已存在，但该模块从 0 开始，需走完整闭环 | [`method/workflows/02-新系统开发.md`](./method/workflows/02-新系统开发.md) |
| **场景 3：功能迭代 / Bug 修复** | 系统已存在，做增量改动 | [`method/workflows/03-功能迭代.md`](./method/workflows/03-功能迭代.md) |

不确定时，**先问用户**，不要猜测。

---

## 三、改动方案先行（强制）

实现任何代码前，AI 必须先输出下列"改动方案"，等用户确认后再动手：

- **影响范围**：涉及哪些模块、端、依赖服务
- **涉及文件**：预计新增 / 修改 / 删除的文件清单
- **接口变化**：新增 / 修改的 API 路径、方法、请求/响应结构
- **表结构变化**：新增 / 修改的表、字段、索引（含 DDL 草稿）
- **风险点**：兼容性、数据迁移、性能、权限
- **实施顺序**：建议步骤（如：表结构 → 后端 → 管理端 → 用户端）

模板见 [`method/templates/改动方案模板.md`](./method/templates/改动方案模板.md)。

**实现原则**：不要修改已有方法的参数；如需扩展，优先新增方法或新接口，避免影响现有功能。

## 四、目录地图

```
ai_workspace/
├── AI_CONTEXT.md            ← 你正在读的文件（唯一入口）
│
├── method/                  ← 方法论本体（跨项目通用，不要改）
│   ├── workflows/             三类场景的标准流程
│   ├── templates/             所有交付物的模板（PRD、设计、接口、UI 提示词等）
│   ├── specs/                 通用规范（接口设计、数据库、文档、代码、UI）
│   ├── prompts/               常用提示词
│   └── guides/                指南（ai_files 使用规则、新项目套用指南）
│
├── project/                 ← 项目特定内容（每个项目自己长）
│   ├── 项目介绍.md            ★ 端清单、代码结构、技术栈，AI 必读
│   ├── designs/               项目整体设计成果（产品、架构、数据库）
│   ├── apis/                  接口文档成品
│   └── ai_files/              AI 自治笔记（QA、理解、决策）
│
└── features/                ← 功能/迭代实例
    └── {编号}-{名称}/         单个功能目录
        ├── {编号}-{名称}.md     功能主文档（含每次迭代）
        ├── CHANGELOG.md         变更日志
        └── outputs/             该功能的交付物（SQL、路由、UI 提示词等）
```

## 六、功能编号与目录约定

- 功能目录命名：`features/{编号}-{名称}/`，例：`features/109-内容整理优化/`
- 编号由用户分配（通常对齐外部任务系统编号）
- 功能主文档与目录同名：`features/109-内容整理优化/109-内容整理优化.md`
- 每次新迭代在主文档中追加"迭代-xx"小节
- 该功能产生的所有交付物（SQL、路由配置、UI 提示词、联调记录等）都放在 `outputs/`

---

## 七、AI 自治规则（`project/ai_files/`）

AI 可主动往 `project/ai_files/` 写笔记，但必须遵守 [ai_files 使用规则](./method/guides/ai_files使用规则.md)。

**简版**：
- ✅ 该存：跨迭代有价值的理解/决策/QA、易踩坑的事、调用链梳理
- ❌ 不存：代码能直接读到的、一次性的、与 git 历史重复的
- 命名：`{功能编号}-{话题}.md` 或 `topic-{主题}.md`

---

## 八、沉淀义务（功能完成时必做）

每完成一次迭代或功能，AI 必须：

1. 更新该功能主文档的"任务状态"（已完成 / 进行中 / 待开始）
2. 在该功能目录的 `CHANGELOG.md` 中追加一条
3. 交付物归位到 `outputs/`：SQL、管理端路由配置、API 接口文档、UI 提示词
4. 必要时往 `project/ai_files/` 写决策/踩坑笔记

---

## 九、协作铁律

- **入口唯一**：所有任务从本文件开始，不绕过。
- **先方案后实现**：第三节流程跳不得。
- **模板优先**：所有交付物都从 `method/templates/` 取模板填写，不要自创格式。
- **不猜，多问**：有疑问先暂停询问，写到迭代文档的"AI 疑问"区。
- **不破坏现有功能**：不动已有方法签名；扩展优先于修改。
