# `project/ai_files/` 使用规则

> 目的：让 AI 把"跨迭代有价值"的理解、决策、QA 沉淀下来，下次少走弯路；同时避免目录被噪声填满。

---

## 一、什么该存（✅）

- **跨迭代复用的理解**：模块调用链、关键状态机、复杂业务规则的解读
- **踩坑与解决**：调试过的问题、根因、绕过办法
- **决策记录**：在多种方案中为何选 A 而非 B（含当时的约束）
- **外部依赖说明**：第三方服务的怪异行为、限速规则、字段含义
- **环境与配置陷阱**：开发/测试/生产环境差异、易出错的配置组合
- **未决问题**：暂时绕过但需要日后处理的点

## 二、什么不该存（❌）

- 代码里能直接读到的事实（如"xxx 方法在 file.go:42"）
- 一次性、用完即丢的中间笔记
- 与 git 历史重复的信息（提交说明已涵盖）
- 已经写在功能主文档、CHANGELOG、设计文档里的内容
- 项目级文档应有的内容（应写到 `project/designs/` 而非 `ai_files/`）

## 三、命名

- 关联功能：`{功能编号}-{话题}.md`，例 `109-流式接口与通用 AI 调用关系.md`
- 跨功能主题：`topic-{主题}.md`，例 `topic-鉴权 token 刷新机制.md`
- 决策记录：`decision-{编号}-{主题}.md`

## 四、文件结构（推荐）

```markdown
# {标题}

> 创建：YYYY-MM-DD
> 关联：features/{x}/、issue#xxx（如有）

## 背景
（为什么需要这份笔记）

## 核心内容
（理解 / 决策 / 踩坑 / 规则）

## 影响范围
（哪些模块/接口/迭代会用到这些信息）

## 待办（如有）
- [ ] xxx
```

## 五、何时写

- 调研/理解到了**非显然**且**会复用**的事
- 解决了**会再次遇到**的问题
- 做了**未来需要解释**的决策
- 发现了**容易踩坑**的点

## 六、何时更新 / 删除

- 笔记内容已过时：**及时更新或删除**，不要留下误导性信息
- 笔记内容已被吸收进正式文档（如规范、设计文档）：删除并在新文档处保留指针
- 笔记被多次引用且稳定：考虑升级到 `project/designs/` 或 `method/`

## 七、自检三问

写之前问自己：
1. 这是"代码读不出来"的事吗？
2. 下次迭代/排查会回来看吗？
3. 一个月后我还能看懂吗？

三个 yes → 写；任一 no → 不写。
