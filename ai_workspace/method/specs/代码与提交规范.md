# 代码与提交规范

> 通用代码与 Git 提交规范，技术栈无关。

---

## 一、代码

### 命名
- 含义清晰、避免缩写（除非领域通用）
- 函数动词开头：`getUser`、`calculateTotal`
- 布尔变量用 `is/has/should` 前缀
- 常量全大写下划线：`MAX_RETRY_COUNT`

### 注释
- 默认不写注释——好命名 + 简洁结构胜过注释
- 该写的注释：**WHY 而非 WHAT**——非显然的约束、踩坑原因、引用的外部文档
- 不写"本次修改"、"用于 X 调用"等会过时的注释

### 函数 / 方法
- 单一职责，一个函数做一件事
- 参数不超过 4 个，更多用对象/结构体
- 避免布尔参数（用枚举或分裂函数）
- 早返回（early return），减少嵌套

### 错误处理
- 错误不吞：要么处理要么向上抛
- 错误信息携带上下文（哪个操作失败、关键参数）
- 边界做校验，内部信任内部调用

### 不做过度设计
- 不为假想的未来需求加抽象
- 三处相似优于一处不准确的抽象
- 不引入未使用的依赖

### 安全
- 输入校验在边界完成
- 不要把敏感信息写日志
- 不要在前端做最终权限校验

---

## 二、Git 提交

### Commit Message 格式
```
{type}: {简短描述}

{可选正文：why、影响、关联}
```

**type**：
- `feat` 新功能
- `fix` bug 修复
- `refactor` 重构（无功能变更）
- `docs` 文档
- `style` 格式（不影响逻辑）
- `test` 测试
- `chore` 构建/配置/杂项
- `perf` 性能

### 原则
- 一次提交只做一件事（一个 type、一个主题）
- 描述用中文或英文，项目内统一
- 不要混合无关改动
- 不要提交临时代码、调试日志、注释掉的代码

### 分支
- 主干：`main`（或 `master`）
- 功能：`feature/{编号}-{简述}`
- 修复：`fix/{编号}-{简述}`
- 发布：`release/x.y.z`（如启用）

### 提交频率
- 完成一个最小可验证的单元就提交
- 避免大爆炸式提交

### 不允许
- 直接 push 主干（走 PR / MR）
- 强推已合并分支
- 提交密钥、token、`.env` 等敏感文件
