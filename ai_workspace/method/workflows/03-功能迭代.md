# 场景 3：功能迭代 / Bug 修复

> 触发：系统已存在，只是做增量改动（新增小功能、优化、bug 修复）。
> 目标：轻量、可追溯。

---

## 流程总览

```
需求
  ├─ 1. 定位功能目录（或新建）
  ├─ 2. 新增"迭代-xx"小节
  ├─ 3. 走迭代五步：用户需求 → AI 疑问 → 需求梳理 → 拆分任务 → 任务状态
  ├─ 4. 改动方案先行（等确认）
  ├─ 5. 实现 + 必要交付物（SQL / 接口文档差异 / 路由 / UI）
  └─ 6. 沉淀（CHANGELOG / ai_files）
```

---

## 迭代五步（核心）

在 `features/{x}/{x}.md` 内追加：

```markdown
## 迭代-xx

### 用户需求
（粘贴用户原话或精炼后的需求）

### AI 疑问
（不清楚的地方列在这里，暂停询问用户）

### 需求梳理
（确认后的最终需求理解）

### 拆分任务
1. ...
2. ...

### 任务状态
- 已完成：...
- 交付文件：
  - SQL：...（或"无"）
  - 管理端路由配置：...（或"无"）
  - API 接口文档：...（或"无"）
```

模板：[功能迭代模板](../templates/功能迭代模板.md)

---

## 改动方案先行

需求梳理完成后、动手前，按 [改动方案模板](../templates/改动方案模板.md) 输出方案，**等用户确认**。

涉及面非常小（如改一个常量、修一个明显 typo）时可省略，但要在迭代文档里说明"无需方案，直接修复"。

---

## 实现原则

- **不动已有方法签名**：参数变化容易破坏现有调用方
- **能新增就不修改**：扩展时优先新增方法/接口
- **小步快跑**：每步可独立验证

---

## 完成时必做

1. 更新本迭代的"任务状态"
2. `features/{x}/CHANGELOG.md` 追加一条
3. 该功能有外部清单的话（如项目级功能清单），同步更新
4. 把决策/踩坑写 `project/ai_files/`
